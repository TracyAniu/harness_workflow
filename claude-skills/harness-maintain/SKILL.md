# harness-maintain：熵回收与规则升级

Agent 会复制仓库里已有的模式——包括坏模式；文档会腐烂；同样的错误会重复出现。技术债要小额、持续偿还，而不是攒到一起集中痛苦处理。本 skill 做三件事：清理熵、归档计划、把"口头提醒"升级为"自动机制"。

三件套之一：`harness-init`（建轨道）→ `harness-task`（跑轨道）→ `harness-maintain`（本 skill）。

## 1. 收集信号

- `tasks/lessons.md`：哪些教训出现了 ≥2 次？
- `git log` 近期历史与近期 review 意见：哪些修正在反复发生？
- `docs/` vs 代码：文档描述与实际行为、目录结构、命令是否还一致？
- `docs/exec-plans/active/`：有没有实际已完成或已废弃的计划还躺在 active？
- 代码漂移：重复造的 helper、越过 ARCHITECTURE.md 模块边界的依赖、与 AGENTS.md 规则冲突的新代码。

## 2. 升级强度阶梯

对每个反复出现的问题，沿这个阶梯**尽量往上推**——能自动强制的就不要停留在文档提醒：

1. **文档规则**：docs/ 或 AGENTS.md 里加一条明确规则。
2. **模板/脚手架**：让正确做法成为默认路径。
3. **lint 规则 / 结构测试**：自动检查，违反即报。
4. **脚本 / CI 强制**：违反即失败，无法合入。

`tasks/lessons.md` 中已升级为机制的条目标注"已固化为 X"，防止清单无限膨胀。

## 3. 清理动作

- 修正过期文档，使之与代码一致（冲突时以代码为准）。
- 已完成的 exec-plan：补上"完成记录"，移入 `docs/exec-plans/completed/`。
- 已废弃的计划：注明废弃原因后归档或删除。
- 发现的代码漂移：小的直接修（一次 commit 只修一类问题）；大的立一个 exec-plan 或 tech-debt 条目，**不要顺手做大重构**。

## 4. 汇报

- 清理了什么（文档 / 计划 / 代码），各自的 commit。
- 升级了哪些规则、升到了阶梯第几层。
- 哪些问题需要用户拍板（例如要不要引入某条 lint 强制、要不要删除某个疑似废弃模块）。
