# harness-maintain：熵回收与规则升级

Agent 会复制仓库里已有的模式——包括坏模式；文档会腐烂；同样的错误会重复出现。技术债要小额、持续偿还，而不是攒到一起集中痛苦处理。本 skill 做四件事：控制开工必读文件的体积、清理熵、归档计划与任务记录、把"口头提醒"升级为"自动机制"。

三件套之一：`harness-init`（建轨道）→ `harness-task`（跑轨道）→ `harness-maintain`（本 skill）。

## 1. 收集信号

- 开工必读文件的体积：项目 CLAUDE.md、AGENTS.md 及其 `@` 导入、`tasks/todo.md`、`tasks/lessons.md`。它们每轮都会被读进上下文，用 `wc -l` / `wc -c` 实测，不要估。参考预算：AGENTS.md ≤ 150 行，todo.md ≤ 200 行，lessons.md ≤ 60 行；超出就在第 3 步清理。
- `tasks/todo.md`：已完成的任务块是否还留在里面？剩下的未勾选项，哪些已被 exec-plan 接手或已作废？
- `tasks/lessons.md`：哪些教训出现了 ≥2 次？有没有写成长篇事故经过、而不是能直接照做的规则？
- `git log` 近期历史与近期 review 意见：哪些修正在反复发生？
- `docs/` vs 代码：文档描述与实际行为、目录结构、命令是否还一致？
- `docs/exec-plans/active/`：有没有实际已完成或已废弃的计划还躺在 active？
- 代码漂移：重复造的 helper、越过 ARCHITECTURE.md 模块边界的依赖、与 AGENTS.md 规则冲突的新代码。

## 2. 升级强度阶梯

对每个反复出现的问题，沿这个阶梯**尽量往上推**——能自动强制的就不要停留在文档提醒：

1. **文档规则**：docs/ 或 AGENTS.md 里加一条明确规则。
2. **模板/脚手架**：让正确做法成为默认路径。
3. **lint 规则 / 结构测试**：自动检查，违反即报。
4. **脚本 / CI 强制**：违反即失败，无法合入。

例：todo.md 反复膨胀 → 在 `scripts/check.sh` 里加行数检查，超出预算就报。

`tasks/lessons.md` 中已升级为机制的条目标注"已固化为 X"，防止清单无限膨胀。

## 3. 清理动作

- 修正过期文档，使之与代码一致（冲突时以代码为准）。
- 已完成的 exec-plan：补上"完成记录"，移入 `docs/exec-plans/completed/`。
- 已废弃的计划：注明废弃原因后归档或删除。
- `tasks/todo.md` 归档：一个任务块 = 一个顶级 `# ` 标题到下一个顶级标题（代码块里的 `#` 不算）。已完成的块原样移入 `tasks/todo-archive.md`，保持原顺序（新的在前），文件头注明移入日期；todo.md 只留进行中的块和"当前状态"块。随块归档的未勾选项，把原文抄回 todo.md 并注明出自哪个任务，由用户勾掉或删除——不替用户判定作废。
- `tasks/lessons.md` 精简：每条压成 1–2 行、能直接照做的规则；事故经过移到 `tasks/fixed-issues-history.md`；已固化为机制的条目只留"已固化为 X"一行，或直接删除。
- 搬移类改动必须证明无损：把"保留部分 + 归档正文（去掉文件头）"与 `git show HEAD:<原文件>` 逐字节比对。注意换行：Windows 上检出的文件可能是 CRLF，而 git 里存的是 LF，比对前先按检出的换行换算。保持原文件的编码、BOM 与换行。
- 改 skill、模板或全局片段：先查清它由哪个仓库或安装器生成，只改源头再重装；只改安装后的副本，下次安装就被覆盖。
- 发现的代码漂移：小的直接修（一次 commit 只修一类问题）；大的立一个 exec-plan 或 tech-debt 条目，**不要顺手做大重构**。

## 4. 汇报

- 清理了什么（文档 / 计划 / 任务记录 / 代码），各自的 commit。
- 开工必读文件清理前后的实测行数和字节数。没有实测，就不要宣称省了多少 token。
- 升级了哪些规则、升到了阶梯第几层。
- 哪些问题需要用户拍板（例如要不要引入某条 lint 强制、要不要删除某个疑似废弃模块）。
