# harness-task：一轮标准开发任务

每轮会话是一次接力：从上一轮留下的干净状态出发，推进**一个**明确目标，再以干净状态交还。任务状态写在文件和 git 里，不依赖聊天记忆。

三件套之一：`harness-init`（建轨道）→ `harness-task`（本 skill）→ `harness-maintain`（养轨道）。项目没有 harness 结构也可用本流程，记录位置退化为 `tasks/todo.md`。

## 1. 开工检查（不可跳过）

1. 读 `AGENTS.md`（或 CLAUDE.md）与本任务相关的 `docs/`。
2. `git status` + `git log --oneline -10`：确认工作区干净、了解近期发生了什么。工作区不干净时先向用户确认怎么处理，不要在脏状态上叠加改动。
3. 读进度：`docs/exec-plans/active/` 下的活跃计划、`tasks/todo.md`。
4. 跑冒烟：`./scripts/smoke.sh` 或等价方式，确认主流程当前没坏。**先修再做**——基础已坏的话，修复它就是本轮第一个任务。

## 2. 定任务与计划

- 一次只推进一个明确目标（一个功能 / 一个 bug / 一个重构），宁小勿大；大目标拆开，分多轮接力。
- 单会话可完成 → 在 `tasks/todo.md` 顶部写带 checkbox 的计划。
- 跨会话/多文件的复杂任务 → 按 `docs/exec-plans/template.md` 在 `docs/exec-plans/active/` 新建（或续写已有）执行计划。
- 非平凡任务按用户全局规范先进 plan mode，计划确认后再实现。

## 3. 小步实现

- 用最小变更完整解决问题；复用仓库既有模式；不做与任务无关的重构。
- 中途发现计划与现实不符：停下，改计划（同步改到计划文件里），再继续。

## 4. 验证（完成的唯一标准）

- 跑 AGENTS.md 完成标准里列出的全部相关验证（check / test / smoke）。
- 用户可见的改动必须走端到端真实路径：Web UI 用浏览器实际操作（有 Playwright/DevTools 就自动化），CLI 实际执行命令。只有单测通过或 curl 返回 200 不算"用户能用"。
- **生成与评估分离**：重要改动或主观质量改动（UI、架构调整）完成后，请独立评审再收工——用 `/code-review`、codex:rescue 或子 agent 以挑错视角过一遍，不要只靠自评（自评天然过于乐观）。
- 某项验证跑不了：如实说明原因与剩余风险；绝不把"看起来完成"报告为完成。

## 5. 记录与交接（干净状态契约）

每轮结束时仓库要像"准备合入主分支"一样：无明显 bug、有验证记录、有提交、有说明。

1. 更新进度：`tasks/todo.md` 勾选并补 Review 小节；exec-plan 追加一条 Progress Log（做了什么 / 验证了什么 / 下一步从哪继续）。
2. 行为、架构或工作流有变化 → 同步更新对应 docs。
3. 验证通过后小步 commit，message 说清这轮做了什么——git history 是跨会话记忆的一部分。
4. 有教训 → 以可复用规则的形式记入 `tasks/lessons.md`。
5. 汇报：改了什么 / 跑了哪些验证及结果 / 剩余风险 / 建议 review 的关键文件。

## 上下文快耗尽时

不要硬撑到被截断：立即停止开新改动，把当前状态按第 5 步完整落盘（进度文件 + commit + "下一步"说明），让下一轮无损接力。半成品宁可回滚，也不要留在工作区里让下一轮猜。
