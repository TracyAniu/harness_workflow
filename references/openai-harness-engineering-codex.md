# OpenAI Harness Engineering：在智能体优先的世界中利用 Codex

## 一句话总结

这篇文章的核心观点是：当智能体成为主要编码者后，工程师的主要工作会从“写代码”转向“设计环境、编码约束、组织上下文、构建反馈回路”。软件工程的纪律没有消失，只是从代码本身上移到了仓库结构、工具链、文档系统、自动化验证和控制系统。

## 背景

OpenAI 团队做了一个五个月实验：构建并交付一个内部 beta 产品，约束是没有一行代码由人类手写。产品代码、测试、CI、文档、可观测性、内部工具、评审回复、仓库管理脚本等，都由 Codex 生成。

结果：

- 约五个月内形成约一百万行代码。
- 约 1,500 个 PR 被打开和合并。
- 早期只有 3 名工程师驱动 Codex，后来扩大到 7 名。
- 产品已被内部日活用户和外部 Alpha 测试者使用。
- OpenAI 估计花费约为传统手写代码所需时间的 1/10。

文章的关键句可以概括为：人类掌舵，智能体执行。

## 从空 Git 仓库开始

这次实验不是在已有代码库里让 Codex 补功能，而是从空 Git 仓库开始。首次提交发生在 2025 年 8 月下旬，初始仓库结构、CI、格式化规则、包管理器配置、应用框架，甚至初始 `AGENTS.md`，都由 Codex CLI 在少量模板指导下生成。

这说明 OpenAI 的重点不是“让 agent 接管已有代码”，而是从第一天起就让仓库按照 agent-first 的方式演化：

- 初始模板给出最小方向。
- Codex 生成项目骨架和开发约束。
- 仓库里的代码、文档、CI 和工具从一开始就是 agent 可读、可改、可验证的。
- 后续所有工程知识继续沉淀进仓库，而不是留在外部文档或人脑中。

这对新项目很有启发：如果项目还没复杂到不可调整，越早建立 `AGENTS.md`、`docs/`、执行计划、验证脚本和自动化约束，后续 agent 协作成本越低。

## 工程师角色的变化

在人类不直接写代码的约束下，工程师的工作重点变成：

- 定义任务和验收标准。
- 设计系统结构和边界。
- 为 Codex 提供工具、抽象和上下文。
- 建立可执行、可验证、可恢复的反馈循环。
- 把失败看成系统信号：缺的是工具、约束、文档，还是测试能力。

当 Codex 卡住时，解决方案不是让它“再努力一点”，而是追问：要让智能体可靠完成这个任务，它还需要什么能力？这个能力如何变成代码库中清晰、可发现、可强制执行的东西？

## Agent-to-agent review 循环

文章里一个容易被忽略的点是：人类并不是每个 PR 都亲自深度 review。随着系统成熟，很多 review 变成 agent-to-agent 的流程。

典型循环是：

1. 人类用 prompt 描述任务。
2. Codex 在本地实现并打开 PR。
3. Codex 自己先本地审核改动。
4. 再请求本地或云端的其他 agent 做专项 review。
5. Codex 根据人类或 agent 的反馈修改。
6. 循环直到 review agent 满意。
7. 必要时人类再介入判断。

这套循环依赖标准开发工具，而不是靠人复制粘贴上下文。Codex 会直接使用 `gh`、本地脚本、仓库内技能和文档来收集信息、回应评论、推送更新。

这里的关键不是“完全不需要人 review”，而是把大量机械性 review 和修复循环从人类注意力中移走。人类保留方向判断、验收判断和高风险决策。

## 让应用对智能体可读

随着代码生成吞吐量上升，瓶颈变成人类 QA。OpenAI 的做法是让应用的 UI、日志、指标和追踪数据直接对 Codex 可读。

关键做法：

- 每个 git worktree 可以启动一个独立应用实例。
- Codex 能通过 Chrome DevTools 协议驱动应用、获取 DOM 快照、截图、导航并验证 UI 行为。
- 每个任务都有临时本地可观测性栈，任务结束后日志和指标一起销毁。
- Codex 可用 LogQL 查询日志、PromQL 查询指标、TraceQL 查询追踪。

这样，提示可以从“修一下性能”变成更可执行的形式，例如：

- 确保服务启动在 800ms 内完成。
- 四个关键用户旅程中的任何 span 都不得超过 2 秒。

这里的重点是：把原本只有人能观察的运行时信号，变成 agent 可查询、可推理、可闭环验证的输入。

## 把代码仓库作为记录系统

文章最重要的工程原则之一是：给 Codex 一张地图，而不是一本 1,000 页说明书。

OpenAI 试过巨大 `AGENTS.md`，后来认为这种方式失败：

- 上下文窗口是稀缺资源，巨型说明会挤占任务、代码和相关文档空间。
- 规则太多会让所有规则都变得不重要。
- 大文档很快腐烂，agent 难判断哪些仍然有效。
- 单一大 blob 难以机械检查覆盖率、新鲜度、所有权和交叉链接。

因此，`AGENTS.md` 不应是百科全书，而应是目录。真正的知识放在结构化 `docs/` 中，仓库本身成为系统记录源。

典型结构包括：

- `AGENTS.md`：短入口，约 100 行，指向其他文档。
- `ARCHITECTURE.md`：顶层架构地图。
- `docs/design-docs/`：设计文档和核心理念。
- `docs/exec-plans/`：活跃计划、已完成计划、技术债务记录。
- `docs/product-specs/`：产品规格。
- `docs/references/`：LLM 可读的外部参考。
- `DESIGN.md`、`FRONTEND.md`、`QUALITY_SCORE.md`、`SECURITY.md` 等专题规则。

这些文档还要被 linter 和 CI 检查：是否过期、是否交叉链接、是否结构正确。OpenAI 还使用周期性的 doc-gardening agent 自动发现过时文档并发 PR 修复。

### 渐进式披露

这套文档结构的设计目的不是让 agent 一次性读完所有内容，而是实现渐进式披露：

- `AGENTS.md` 是稳定入口。
- 顶层架构文档告诉 agent 该去哪里找信息。
- 具体设计、产品规格、执行计划和参考资料按主题分散在 `docs/`。
- agent 只在当前任务需要时读取更深层文档。

这样既节省上下文窗口，又能避免巨大说明书腐烂。对自己的项目来说，`AGENTS.md` 最好只写“导航、规则、命令、完成标准”，不要堆满所有产品和架构细节。

## 目标是 agent readability

文章提出一个很实用的判断框架：从 agent 视角看，运行时上下文中不可访问的东西就等于不存在。

这意味着：

- Google Docs、Slack 讨论、人的隐性知识，如果不进入仓库，就无法被 Codex 使用。
- 代码、Markdown、schema、可执行计划这些本地且版本化的工件，是 agent 最可靠的知识来源。
- 团队共识、架构取舍、产品原则，一旦对未来 agent 有用，就应该编码进仓库。

技术选型也受这个原则影响。文章倾向选择可组合、API 稳定、训练数据中常见、行为可检查的“无聊技术”。有时自己实现一个小而清晰、可测试、可观测的工具，比引入不透明第三方库更适合 agent 长期维护。

## 用规则编码架构与品味

仅靠文档不能维持一个 agent 生成代码库的长期一致性。OpenAI 的做法是强制执行不变量，而不是微观管理实现方式。

他们建立了严格的分层领域架构：

- 每个业务域有固定层级。
- 依赖只能沿固定方向流动。
- 跨领域能力通过显式 Providers 入口进入。
- 规则由自定义 linter 和结构测试强制执行。

他们还把“品味不变式”编码进工具中，例如：

- 结构化日志。
- schema 和 type 命名规范。
- 文件大小限制。
- 平台可靠性要求。
- 架构边界检查。

关键点是：面向人类的团队中，这类规则可能显得繁琐；面向 agent 的代码库中，它们是乘数。规则一旦编码，就能被所有 agent 运行持续应用。

## 高吞吐改变合并策略

当 Codex 生成和修复 PR 的速度远超人类注意力时，传统合并门槛需要调整。

OpenAI 的实践是：

- PR 生命周期尽量短。
- 阻塞合并的 gate 尽量少。
- 偶发测试失败通常靠重跑或后续修复，而不是无限期阻塞。
- 在这个系统里，等待成本高，纠错成本低。

这个结论不是普遍适用的。它依赖高自动化验证、高回滚能力、高 agent 修复吞吐量和成熟反馈循环。在低吞吐、低自动化环境中，这样做会很危险。

## “智能体生成”真正包含什么

文章强调，agent 生成的不只是业务代码，而是整个软件系统：

- 产品代码与测试。
- CI 配置和发布工具。
- 内部开发者工具。
- 文档和设计历史。
- 评估框架。
- PR 评论和回复。
- 管理仓库的脚本。
- 生产仪表板定义。

人类仍然重要，但工作抽象层次变了：排序优先级、把用户反馈转成验收标准、验证结果、识别系统缺口，并让 Codex 自己把缺口修进仓库。

## 人类仍然负责什么

文章并不是说人类退出工程。人类的工作被上移到更高杠杆的位置：

- 决定做什么、不做什么。
- 把用户反馈转成明确验收标准。
- 识别系统缺少的工具、文档和约束。
- 判断哪些规则应该被编码进仓库。
- 对安全、产品方向、架构取舍做最终判断。
- 把个人品味和团队经验转成可持续生效的机制。

因此，agent-first 工程不是降低工程要求，而是要求工程师更擅长设计系统、设计反馈循环和设计可执行约束。

## 自主水平的提升

当测试、验证、评审、反馈处理和恢复流程都被编码进系统后，Codex 可以端到端驱动一个功能：

1. 验证代码库当前状态。
2. 复现已报告 bug。
3. 录制故障演示视频。
4. 实施修复。
5. 运行应用验证修复。
6. 录制修复后演示视频。
7. 打开 PR。
8. 回应 agent 和人类反馈。
9. 检测并修复构建故障。
10. 只在需要判断时交给人。
11. 合并更改。

但文章也明确提醒：这种能力高度依赖该代码库的结构和工具，不应在没有类似投入的情况下假设可以泛化。

## 熵与垃圾收集

完全由 agent 生成的代码库会出现新的维护问题：Codex 会复制仓库中已有模式，包括不理想模式。随着时间推移，这会造成漂移。

OpenAI 起初让人每周五清理“AI 残渣”，占用约 20% 时间，后来改成把“黄金原则”编码进仓库并建立循环清理流程。

例子：

- 优先使用共享工具包，而不是重复手写 helper。
- 不允许基于猜测去探测数据形状；要在边界验证，或依赖类型化 SDK。
- 周期性后台 Codex 任务扫描偏差、更新质量等级、发起重构 PR。

这相当于代码库的垃圾回收。技术债务要小额、持续偿还，而不是累积后集中痛苦处理。

## 仍未解决的问题

OpenAI 认为这个策略在内部发布和采纳中表现不错，但仍有未解问题：

- 完全 agent 生成的系统，架构连贯性会如何长期演化？
- 人类判断力最适合介入哪些环节？
- 如何把人类判断力编码成可持续作用的系统？
- 模型能力增强后，当前 harness 和控制系统应如何演变？

他们的结论是：软件工程仍然需要纪律，只是纪律更多体现在支撑结构上，而不是手写代码上。

## 和 Anthropic 两篇文章的关系

Anthropic 更关注长程 agent 如何跨上下文、跨会话完成任务：initializer、feature list、progress file、git commit、evaluator、QA 循环。

OpenAI 这篇更进一步，讨论当整个工程系统都围绕 Codex 运转时，代码库本身如何成为 agent 的工作环境：

- Anthropic 的关键词是 handoff、incremental progress、evaluation。
- OpenAI 的关键词是 agent readability、repository as record、encoded constraints、observability、garbage collection。

两者合起来看，可以得到一个完整方向：要让 agent 做长程软件工程，不能只优化 prompt；必须重构工程环境，让知识、约束、反馈和质量标准都进入可执行系统。

## 可操作清单

如果要把这篇文章落到自己的工程实践，可以从这些点开始：

1. 保持 `AGENTS.md` 短小，把它做成目录而不是百科全书。
2. 把架构、产品原则、设计规范、技术债务和执行计划版本化进仓库。
3. 为 agent 提供可运行、可观测、可验证的本地环境。
4. 让 agent 能直接访问 UI 状态、日志、指标和 trace。
5. 用自定义 lint 和结构测试强制架构边界。
6. 把反复出现的 review 意见升级为规则或工具。
7. 把人类隐性知识转为 Markdown、schema、测试或脚本。
8. 对复杂任务使用可执行计划，并把进度和决策日志提交到仓库。
9. 定期运行文档修剪和技术债清理 agent。
10. 谨慎调整合并策略；只有自动验证和修复吞吐量足够高时，才降低阻塞门槛。

## 新项目落地配置

如果要把这篇文章的方法迁移到一个新工程，可以优先建立这些文件和目录：

```txt
AGENTS.md
ARCHITECTURE.md
docs/
  product-specs/
  design-docs/
  exec-plans/
    active/
    completed/
    tech-debt-tracker.md
  references/
  FRONTEND.md
  RELIABILITY.md
  SECURITY.md
  QUALITY_SCORE.md
scripts/
  dev.sh
  typecheck.sh
  lint.sh
  test.sh
  smoke.sh
```

最低要求是让 agent 能回答四个问题：

1. 这个项目是什么，哪些需求是核心？
2. 系统如何组织，哪些边界不能破坏？
3. 当前任务应该怎么拆、怎么记录、怎么接力？
4. 修改后怎么证明它真的工作？

这些答案越多地存在于仓库、脚本、测试和 lint 中，越少依赖聊天上下文和人的临时提醒，agent 开发就越稳定。

## 我的理解

这篇文章的真正重点不是“Codex 能写一百万行代码”，而是 OpenAI 为了让 Codex 能可靠写一百万行代码，重建了工程操作系统。

过去工程组织靠人脑、会议、Slack、经验和 code review 维持一致性；agent-first 代码库必须把这些东西显式化、结构化、版本化、可检查化。谁能更快把隐性判断编码进工具和仓库，谁就能获得更高的 agent 杠杆。
